## 1. Concept and Architecture

Exo is a VS Code extension that provides an interface to an autonomous AI agent via the ACP (Agent Communication Protocol).

**Architecture — three-tier stack:**
1. **ACP Agent** (external process): the "brain". Accepts requests, plans tasks, decides which tools to invoke, produces responses. Communicates over `stdio`.
2. **Extension Host** (Node.js/VS Code): a thin proxy. Manages agent process lifecycle, relays messages between agent and UI, implements system handlers (file access, permission flow, VS Code API).
3. **Webview UI** (Preact): sidebar UI. Renders chat, session list, plan widget, tool cards.

**Main data flow:** `User` → `Webview UI` → `Extension Host` → `ACP Agent` → `Extension Host` → `Webview UI` → `User`.

**Key UI behaviors:**

- **Input area:** `@`-mention attaches files (fuzzy-matched); `/`-slash commands advertised by agent. Draft text + attached-file chips are **per-session** — each session id owns its draft (host `Map<sessionId, DraftState>`), so switching sessions swaps the input content, a new session starts with an empty draft, and returning to a session continues the draft. Drafts persist across view switches and VS Code restarts; deleted sessions drop theirs. Images are NOT persisted (deliberate — base64 weight).
- **Auto-Allow Lock:** toggle at the start of `#controls-row` (before mode dropdown). Green/locked (`safe`, default) = standard permission flow; red/open (`auto`) = all `session/request_permission` requests are auto-approved client-side without a card or Diff Editor. Non-persistent (resets on every startup/session load).
- **Attachments:** three channels converge on two in-memory arrays in `MessageInput` (`attachedFiles: string[]`, `images: AttachedImage[]`): `@`-mention, drag-drop of file paths (validated host-side — folders rejected), and drag-drop/paste of images (capability-gated by `canPromptImage`).
- **File/image chips:** editable chips before send; read-only variants render under each user message in history.
- **Session header:** single title bar, no tab strip. Left trigger = chevron + open-session count; current session in the middle (colored session-number badge, status-coded idle/running/awaiting, + title + tiny agent caption); context pill (`200k/1m`, tinted static green/yellow/red by fill: <50% / ≤70% / >70%) on the right. While any session awaits permission the trigger turns warning-tinted with a pulsing awaiting-count badge. The trigger opens one merged dropdown: open sessions (numbered badges, close `×` on hover), "New session" entry, recent sessions (plain dot, relative time, delete `×`; already-open entries filtered out). Closes on ESC / outside click; the `exo.newSession` host command opens the same menu via `showSessionPicker`. Agent identity = `title || name` + optional `v{version}`.
- **Session titles (three sources, ordered):** 1) native `session_info_update` — applied immediately, wins over everything; 2) `session/list` polling — on the first real user message of a session that still has a placeholder title (`New Chat`/`Chat`/`Untitled`/opencode's `New session - <ISO>`), Exo polls `session/list` every 5s (max 5 min) and applies the first non-placeholder title the agent reports; 3) client-side fallback — the first user message's first line (clamped ~48 chars + `…`) is shown as the tab title until a real one arrives. Polling stops on real title, timeout, disconnect, tab close/delete, or `session_info_update`. All three funnel through `applySessionTitle` (runtime + tab list + registry + UI). The poller matches entries by the **agent-owned** `sessionId` (== `runtime.id`).
- **Session id ownership:** the runtime id IS the agent's `sessionId` from `session/new` — Exo never invents its own ids. `runtime.id` is mutable and assigned in `spawnSession` after the agent returns the id (`runtime.id = runtime.acpClient.sessionId ?? sessionId`); `SessionRuntimeCallbacks` read `runtime.id` lazily via a `getId()` getter. All agent-facing calls (`session/load|resume|close|delete`, `session/list` matching) use this id.
- **Session navigation:** switching / opening an item from the header menu is a pure UI view change — live ACP sessions keep running in the background. Closing a session (`×` in the menu) kills the agent process; the session remains in the recent list. Only `deleteSession` removes it permanently (and, for git-worktree sessions, warns when the worktree has uncommitted changes or commits absent from main — otherwise deletes silently).
- **Optimistic UI / loading states:** session ops split into "optimistic" (UI state is ours) and "loader" (must wait for the agent). `closeTab`/`deleteSession` are optimistic — the tab/recent entry disappears instantly, agent teardown runs in the background. `newSession` is optimistic in the other direction: the webview immediately shows an empty chat + input (via `showChat` with the temp `pending-<n>` id, plus `updateAgentRunning:false` so no stale lock), and messages typed while the agent spawns are queued (`PendingSession.queuedMessages`, rendered `isQueued` like a reject follow-up) and dispatched when the runtime resolves. Lazy `switchSession` (`load`) cannot be optimistic (messages come from agent replay), so it keeps the instant loading tab (`TabStatus 'loading'`, temp id `pending-<n>`) + full-area `ChatLoading` view via `showChatLoading`. Pending tabs are not persisted, not selectable, and their `×` cancels the in-flight op (spawned agent gets disconnected, no leak). If the user navigates away while a pending op loads, resolve registers the session silently without stealing focus; a queued message still dispatches to the right runtime (via `opts.runtime`).
- **Parallel sessions:** one tab = one `SessionRuntime` = one agent subprocess with its own `AcpClient`, `cwd` (a git worktree, or the shared workspace root when not a git repo), file cache and streaming/permission/plan state. The webview always renders the active tab; updates (`streamChunk`, `updateMessages`) for non-active runtimes are suppressed and full snapshots are sent by `showChat` on switch.

**Key persistence behavior:**
- Sidebar webview uses `retainContextWhenHidden` (set in `extension.ts`), so switching sidebar views keeps the live webview and Preact state intact.
- Extension Host persists three `workspaceState` entries via debounced saves: `exo.chatUiState` (open tab list `[{sessionId,title,cwd,number}]` + active session id), `exo.chatDraft` (per-session record `{ [sessionId]: { text, attachedFiles } }` — no images; legacy single-draft value is migrated to the restored active session; `pending-*` keys never persist), `exo.sessionRegistry` (recent sessions for the header menu: id/title/updatedAt/cwd).
- On webview startup (`handleReady`), host restores these and reconnects the ACTIVE tab's agent via `session/load` or `session/resume`; the other persisted tabs stay lazy (header-only) and spawn their agent on first click. Session content comes from agent replay and remains agent-owned.

**Key assistant-message behavior:**
- Assistant markdown turns resolved workspace file paths into clickable pill-style links (`<a class="file-link">`). Bare paths, inline-code paths, and optional `:line`/`:line-endLine` suffixes are supported. Fenced code blocks are never linked. Resolution is a two-step contract: `MessageBubble` extracts candidates → host confirms file exists → re-render with cached links.
- **Math (KaTeX):** crash-safe — `marked-katex-extension` with `throwOnError: false`, a pre-parse `sanitizeInlineMath` pass escapes non-LaTeX `$` spans (e.g. `$HOME`, `${x}`), and `marked.parse` is wrapped in try-catch. Display math `$$...$$` is untouched.
- **Error Boundary:** message list wrapped in Preact `ErrorBoundary`; a malformed chunk shows a fallback with retry instead of white-screening the chat.

## 2. Technology Stack

- **Language:** TypeScript (strict mode).
- **Environment:** VS Code Extension API (`engines.vscode: ^1.73.0`).
- **Communication protocol:** `@agentclientprotocol/sdk` (ACP implementation, stdio transport).
- **Frontend:** Preact (`preact` + `preact/hooks`).
- **Bundler:** `esbuild` (CJS for extension, ESM for webview) via `esbuild.mjs`.
- **Configuration:** YAML (`js-yaml`) — list of available agents in `~/.config/exo/config.yml`.
- **Markdown:** `marked` + `marked-katex-extension` + `katex`.
- **Sanitization:** `dompurify`.
- **Syntax highlighting:** `shiki` (synchronous, pure-JS engine — see Section 4).
- **Validation:** `zod`.
- **Icons:** `@fortawesome/fontawesome-free`.

## 4. Key Abstractions

- **ACP Session Lifecycle:** Sessions created (`session/new`), loaded (`session/load` with replay), or resumed (`session/resume` without replay). State fully agent-owned. Push-model: a single `onNotification(session.update)` handler dispatches all update types to callbacks; no ActiveSession/nextUpdate loop.
- **Parallel Session Model:** one tab = one `SessionRuntime` = one agent subprocess (own session). All "session" state (`messages`, `taskCalls`, `permissions`, `Files`, streaming) lives on the runtime; `ChatViewProvider` is a registry. This is pure host orchestration on top of ACP — the ACP protocol is untouched.
- **Pending Session Model (optimistic create, loading load):** `newSession`/lazy `switchSession` register a lightweight `PendingSession` (`pending-<n>` temp id, `mode`, `prevActiveId`, `cancelled`, `queuedMessages`) in `ChatViewProvider._pendingSessions` synchronously. `postPendingView(pending)` renders it: `new` shows an empty chat + input (`showChat`), `load` shows the loading tab + `ChatLoading` view (`showChatLoading`). A `new` pending collects messages typed during the spawn into `queuedMessages` (rendered `isQueued` via the `messages` getter fallback). On success `resolvePendingSession` moves queued messages into `runtime.messages`, then swaps it for the real runtime via `finishSessionOpen(runtime, title, activate)` (`activate` only when the user hasn't navigated away — otherwise the session registers silently); the first queued message is then dispatched via `handleUserMessage(..., { preQueued:true, runtime, queuedMessage })` and the rest drain one per turn in `handleUserMessage`'s `finally`. On failure `failPendingSession` restores `prevActiveId` (a live runtime or another pending — rendered via `postPendingView`) or `showEmpty`; a queued message is dropped (error toast shown). Pending tabs are never persisted, never in `_tabList`/`_sessionRegistry`, not selectable in the menu, and their `×` sets `cancelled` so a late resolve disconnects the spawned agent instead of leaking it. `closeTab`/`deleteSession` are pure optimistic: the UI update happens before any agent round-trip.
- **Worktree-per-session:** new sessions spawn their agent with a fresh `git worktree` cwd (local branch `exo-<N>`, never pushed), living at `<root>/.exo/worktrees/exo-<N>` — INSIDE the repo (hidden from git via `info/exclude`). `N` is the first free number on disk (scanned from existing `exo-<N>` dirs), so the folder/branch name always matches the session's ordinal number (`exo-<N>` terminal + header badge) even after the in-memory counter resets; `newSession` aligns `pending.number` with the worktree number. Being children of the trusted repo root keeps them workspace-trusted when the managed workspace switches the Explorer folder. Non-git workspaces fall back to the shared workspace root. `git.detectWorktrees` (on by default in VS Code) picks worktrees up in the SCM view automatically; `registerWorktreeInScm` makes them appear explicitly.
- **Managed Workspace Mode (Explorer-follow):** VS Code can swap workspace folders WITHOUT a window reload only in a multi-root (`.code-workspace`) window; from a single-folder window any root change forces a reload. The extension host is additionally restarted when the FIRST folder (`workspace.rootPath`) changes, so Exo keeps `folders[0]` a stable empty folder (`<root>/.exo/workspace-stable`, displayed as `.exo`; inside the repo so workspace trust never drops to Restricted Mode) and live-switches only `folders[1]` to the active session's worktree (or back to the root) via `WorkspaceFolderSwitcher` → `updateWorkspaceFolders(1, 1, …)` (no reload, serialized + coalesced). Onboarding is a BLOCKING screen (`WorkspaceModeRequired`, no dismiss): in a single-folder, trusted, git window the webview renders "Open as Exo workspace" with a single button (`enterWorkspaceMode` → `enterManagedWorkspace` writes `[stable, root]` and reloads once); the repo root is pinned in `globalState` (`exo.workspaceRoot`) BEFORE the reload and drives `getWorkspaceRoot()` — it never follows the Explorer. Unconditional — no opt-out setting. Structurally exempt (no blocking screen): non-git folders (no worktrees to follow), user-owned multi-root workspaces (never touched — `isManagedWorkspace` shape guard), untrusted windows. Legacy sibling worktrees (old layout) are not followed (path must be under the pinned root).
- **Session terminals:** each session gets one `exo-<N>` terminal (N = the session's ordinal number, the same number shown as the colored header badge) — transient, hidden until shown, rooted in the session cwd. Numbers are monotonic (`_nextSessionNumber`): assigned at pending-session creation, carried to the runtime (`SessionRuntime.number`), persisted in the tab list, reused for lazy loads via the persisted number, and reset to 1 when no tabs remain open (never renumbered while sessions are open — a closed `#1` stays free, next session is `#4`). For git sessions the worktree owns the number (`createWorktree` picks the first free `exo-<N>` on disk), so folder/branch/terminal/badge stay identical even after the counter resets; `newSession` re-aligns `pending.number` when they differ. The terminal is created at the START of session creation (`createPendingTerminal`, right after the worktree cwd is known, BEFORE the slow agent spawn) so it never pops up mid-typing; the chat view + input autofocus follow it. The pending-phase terminal is keyed by the pending id and re-keyed onto the runtime on resolve (`transferSessionTerminal`); disposed on pending cancel/fail. Switching to a session brings its terminal forward via `show(true)` — which preserves focus (a `show(false)` would yank focus from the chat input). Color derives from the number (`SESSION_COLOR_KEYS[sessionColorNumber(N)]`, host-side mirror of the webview's `MODE_COLORS`; both must stay in sync) and is sent in `updateTabs` as `colorIndex`, so badge and terminal always match. Names never change — no title-based rename. Disposed on tab close, session delete, full disconnect and agent `onDisconnect` (crash).
- **Three-level Session Persistence:** shortest-lived continuity (tab switches) via `retainContextWhenHidden`; longer-lived (VS Code restarts) via `workspaceState` storing only client-owned state (open tab list + active id + draft). Message history and plan remain agent-owned, restored via ACP replay. The recent-sessions menu is a local registry (`exo.sessionRegistry`), not `session/list` — each agent only knows its own sessions. Three separate debounced keys: `exo.chatUiState`, `exo.chatDraft`, `exo.sessionRegistry`.
- **Session Title Resolution (3 sources, funneled through `applySessionTitle`):** 1) native `session_info_update` — applied immediately, wins, and stops any active poller; 2) `session/list` polling — started by `ensureSessionTitle` on the first real user message of a session still bearing a placeholder title (`New Chat`/`Chat`/`Untitled`/opencode `New session|Child session - <ISO>`); ticks every 5s (max 5 min), applies the first non-placeholder title the agent reports, stops on real title/timeout/disconnect/tab close/delete; re-started on later messages if the previous window expired (agents generate titles lazily). Entries are matched by the agent-owned `sessionId`; 3) client-side fallback — first message's first line (clamped ~48 chars + `…`). Agents are not required to title sessions, so the fallback also serves as the default display name.
- **Edit Review Flow:** For edit-permission requests, client opens VS Code Diff Editor (`exo-diff:` scheme). Diff content (original/proposed) comes from the standard ACP `type:'diff'` content block within `requestPermission.toolCall.content`. Vendor `vendor/opencode/diff.ts` recovers it if opencode omitted it (issue #37266): EditSpec rebuilt from edit rawInput, indentation restored from the file. No unified-diff/args-based fallback beyond that vendor case. Diff opening is deferred for non-active sessions: `handleRequestPermission` stores `pending.editSpec`, `showSessionRuntime` closes the previous session's diffs (`closeSessionDiffs`) and opens the new one's (`openDeferredDiffs`).
- **Permission System (Zero Trust):** Agent requests permission via `session/request_permission` before dangerous actions. Client renders options inline as a tool card; user decision returns to agent via `permissionDecision` postMessage → `resolvePermission` → pending promise. The card's pending state is keyed on `permissionRequestId`+`permissionOptions`, NOT on `ToolCallInfo.status` — status stays ACP-owned, so a `tool_call_update` racing the approval can never hide the card.
- **Auto-Allow Policy Override:** Client-side boolean `ChatViewProvider._autoAllowPermissions` (default `false`, non-persistent). When `true`, `handleRequestPermission` short-circuits: picks first `allow_once` (fallback `allow_always`), marks tool call `success`, skips Diff Editor, returns immediately. If no allow-option exists, falls through to manual flow.
- **Reject-with-Response (Optimistic Queued Follow-up):** Rejecting a permission request with follow-up text renders the message immediately as `isQueued: true` (dimmed, dashed border, spinner). The next queued message (reject follow-up OR an optimistic message typed while a new session spawned) is dispatched in the `finally` block BEFORE `agentRunning=false` is posted, so it runs as a new turn without lock/unlock flicker. The dispatch passes `{ preQueued: true, queuedMessage }`, flipping `isQueued→false` on that exact message (first `isQueued` in history as fallback) instead of pushing a duplicate. Multiple queued messages drain one per turn.
- **Plan-driven Execution:** Client supports both standard ACP `plan` updates AND a vendor-specific fallback (`extractPlanFromToolArgs`) detecting `{todos:[{content,status,priority}]}` shape in tool args. Standard plan takes priority; both map to UI `Plan` (`completed`→`done`).
- **Per-Mode Config Profiles:** `selectConfigOption` snapshots the active session's (mode, model, thought_level) into `globalState` `exo.lastSetupByMode` (`Record<agentId, Record<modeId, { model, effort }>>`) after every successful `setConfigOption`. On a mode switch, the remembered (model, effort) for the new mode is re-applied (values validated against the fresh `configOptions`; missing ones skipped). The agent still picks the default mode/model on session creation — nothing is restored there. `load`/`resume` untouched (session-owned config).
- **Client-Owned Config Selection:** the dropdown selection (`currentValue`) is client-owned — `AcpClient._clientSelection` (configId → value), written only by our own `setConfigOption`. `buildConfigSelectors(configOptions, clientSelection)` shows `clientSelection[id] ?? agentCurrentValue`. Agent pushes (`config_option_update`) refresh the option lists but never flip a committed selection; `rememberSetup` snapshots the committed values, so a late agent re-broadcast can't revert the dropdown or corrupt the remembered record.
- **Unified Trigger Picker:** Single popup state machine in `MessageInput` serves both `@`-file and `/`-command. Active trigger determined by scanning backwards from cursor for nearest unbroken `@` or `/` token; only one picker active at a time.
- **Fuzzy Matching:** `webview-ui/src/fuzzy.ts` — greedy subsequence (fzf-style) with consecutive and boundary bonuses. `indices` drive `<mark class="fuzzy-hit">` highlighting. Server-side ranking authoritative for files; client both filters/ranks and highlights for commands.
- **Sticky Autoscroll Contract:** `MessageList` treats autoscroll as explicit sticky mode. Single `stickToBottom(behavior)` writes directly to `el.scrollTo`; `scrollIntoView` avoided (walks ancestors). Programmatic vs user scroll distinguished via echo-suppression window + distance threshold. `CSS scroll-behavior: smooth` removed from `#messages` (streaming jank); smooth only on explicit user jumps.
- **Global Thin Scrollbar:** Universal `* { scrollbar-width: thin }` + `::-webkit-scrollbar` in `base.css`. No per-component scrollbar overrides.
- **Resolved File-Link Rendering:** Two-step contract — extract candidates → host resolution → re-render with cached pills. Bare text and inline code may link; fenced blocks never. Pill = `<a class="file-link">` with leading `fa-file-lines` icon, monospace, nowrap, link-tinted background via `color-mix`.
- **Crash-Safe Math Sanitization:** Three-layer guard — `sanitizeInlineMath` (escapes non-LaTeX `$` spans) + `markedKatex({ throwOnError: false })` + try-catch around `marked.parse`.
- **Commit & Merge to Main (host-assisted):** the "merge" pill (`canMerge`, gated on `refreshMergeState`) sends the agent a normal user message asking it ONLY to commit — the agent picks the commit message in the conversation's language, but cannot merge itself (`main` is checked out in the ROOT worktree, so `git checkout main` fails in a linked worktree). On turn end (`mergeIntent`), the host calls `mergeWorktreeToMain(runtime.cwd, root)`: resolves `main`, and when the branch has commits absent from main runs `git merge --no-edit <exo-N>` in the ROOT worktree (only commits move; uncommitted files in the session worktree don't block it). Outcome → toast: `clean-merged` offers a non-modal "Delete" (removes session + worktree + branch via `deleteSession`), `merged-dirty` informs that uncommitted files remain (button stays lit), `uncommitted` warns nothing was committed, `conflict` surfaces the git error. `refreshMergeState` is re-run after the merge (the pre-merge run is stale).
- **Tab Close vs Delete:** closing a session kills the agent process but it stays in the recent list (and its worktree stays). Deleting from the menu is the permanent action — it also removes the worktree and safe-deletes its branch (`git branch -d`, only when fully merged) with a confirm prompt when the worktree has uncommitted changes or commits absent from main; otherwise silent. Deleting a session with no live runtime spawns a temporary agent, issues `session/delete`, and kills it (optimistic UI).
- **Attachment Channel Convergence:** `@`-mention, drag-drop paths, and drag-drop/paste images converge on `attachedFiles`/`images` arrays. On send → ACP `ContentBlock[]`: files → `resource_link` (absolute `file://` URI + relative `name`), images → `image` (base64 `data`). Agent cannot distinguish input channel.
- **Image Capability Gating:** `AcpClient.canPromptImage` gates image input end-to-end. Host pushes to webview as `updatePromptCapabilities`; webview forwards to `MessageInput` as `canPromptImage`. When `false`, dropped/pasted images rejected with transient notice; drag overlay text changes. Re-checked on every connect and `showChat`.
- **Theme Token System:** `tokens.css` maps every VS Code theme variable to semantic `--ct-*` aliases; component CSS references only `--ct-*`, never `--vscode-*` directly. Categories: text (primary/emphasis/secondary/muted), link, dropdown, button, bg, code, diff, overlay, shadow, icon. Mode colors (`MODE_COLORS`) reference `--vscode-terminal-ansi*`, pushed as `--ct-mode` CSS variable on `.chat-view`. High Contrast explicitly supported.
- **Syntax Highlighting (Shiki):** Synchronous at module load (`createHighlighterCoreSync` + pure-JS regex engine — no wasm). Slots into `marked.parse` pipeline via `renderer.code`. Theme tracking: host reads `workbench.colorTheme`, pushes name; webview resolves to bundled Shiki id via `THEME_NAME_MAP`, falls back by kind to `dark-plus`/`light-plus`. `themeVersion` bump re-parses rendered blocks. Unknown langs → escaped plaintext.
- **Agent Identity Header Pattern:** Agent identity is session-level metadata, not part of session title. Host pushes `agentInfo` separately; webview renders as subdued secondary label.

## 5. Data Models and Contracts

- **Configuration (`config.yml` / `AgentConfig` / `ExoConfig`):**
    - `AgentConfig`: `id` (string), `type` (`'stdio'`), `command` (string), `args?` (string[]), `env?` (Record<string,string>).
    - `ExoConfig`: `{ agents?: AgentConfig[], [key]: unknown }`.
    - Location: `$XDG_CONFIG_HOME/exo/config.yml` (default `~/.config/exo/config.yml`).

- **`CommandInfo` / ACP `AvailableCommand`:**
    - `name` (string): without leading `/`.
    - `description` (string): shown in picker.
    - `input?` (`{ hint: string } | null`): `input.hint` becomes textarea placeholder after command selection.

- **`AgentInfo`:**
    - `name` (string): required ACP agent name.
    - `title?` (string): optional display title.
    - `version?` (string): optional, used in header labels as `v{version}`.

- **`AttachedImage` (UI-side):**
    - `id` (string): ephemeral client id (React key + removal).
    - `mimeType` (string): e.g. `image/png`.
    - `data` (string): base64 **without** `data:...;base64,` prefix.
    - `name?` (string): optional original filename.

- **`ToolCallInfo` (tool-card model, defined in both `src/chat/types.ts` and `webview-ui/src/types.ts`):**
    - `toolCallId?` (string): ACP call ID.
    - `status`: `pending` | `success` | `error` | `rejected` | `cancelled` (ACP-owned; pending-permission is marked by `permissionRequestId`, not this field).
    - `summary` (string): short action description (from ACP `title`).
    - `args` (Record<string,unknown>): call arguments (from ACP `rawInput`).
    - `result?` (string): tool output text.
    - `kind?` (string): ACP tool kind (`read|edit|delete|move|search|execute|think|fetch|switch_mode|other`).
    - `locations?`: ACP follow-along paths/ranges.
    - `diffContent?`: `{ path: string, oldText?: string|null, newText: string }` — for Diff Editor.
    - `permissionRequestId?` / `permissionOptions?`: for permission flow.

- **`PermissionOptionInfo`:** `optionId`, `name`, `kind` (`'allow_once'|'allow_always'|'reject_once'|'reject_always'`).

- **`ChatMessage`:**
    - `role`: `user` | `assistant`.
    - `blocks`: `MessageBlock[]` — `{ type:'text', content }` | `{ type:'activity', toolCalls, reasoning, reasoningPhases, reasoningActive? }`.
    - `isError?`, `isStreaming?`, `isQueued?` (user-only, optimistic — reject follow-up or a message typed while a new session spawned).
    - `attachedFiles?` (string[], user-only): relative/absolute paths.
    - `images?` (AttachedImage[], user-only).
    - `_lastChunkKind?` (host runtime-only, not serialized): tracks last chunk type for reasoningPhases counter.

- **`Plan` / `PlanItem`:** `id`, `title`, `description`, `status` (`'pending'|'in_progress'|'done'`).

- **`PendingPermission`:** `requestId`, `toolCallId`, `resolve(response)`, `diffKey?` (Diff Editor cleanup).

- **ACP Protocol contracts:**
    - **Requests (Client → Agent):** `agent/initialize` (handshake/capabilities); `agent/session/new|load|resume|close|delete|list`; `agent/session/prompt` (slash commands sent as plain text — agent parses `/`); `agent/session/setConfigOption`; `agent/authenticate` (if `authMethods` present).
    - **Notifications (Agent → Client) via `session/update`:** `agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update`, `plan` (full replace), `usage_update`, `current_mode_update`, `available_commands_update`, `session_info_update`, `config_option_update`. (`plan_update`/`plan_removed` are experimental and ignored.)
    - **Handlers (Agent → Client → Host):** `client/fs/readTextFile|writeTextFile`, `client/session/requestPermission`.

- **Webview ↔ Host postMessage contracts (internal, non-ACP):**
    - **UI → Host:** `ready`; `sendMessage` (`text`, `attachedFiles?`, `images?`); `selectConfigOption` (`configId`,`value`); `toggleAutoAllowPermissions`; `permissionDecision` (`requestId`, `optionId`|`cancelled`, `followUpText?`); `stopGeneration`; `mergeToMain`; `newSession`; `switchSession` (`sessionId`); `closeTab` (`sessionId`); `deleteSession` (`sessionId`); `searchFiles` (`query`); `updateDraftState` (`text`,`attachedFiles`); `openFile` (`path`,`line?`,`endLine?`); `resolveFileLinks` (`requestId`,`paths`); `addDroppedFiles` (`paths`); `openConfig`; `enterWorkspaceMode`.
    - **Host → UI:** `updateMessages`; `updateConfig`; `updatePlan`; `updateCommands`; `updateTabs` (`tabs: [{sessionId,title,status,colorIndex,number}]`, `activeSessionId`); `updateSessions` (recent list: `[{sessionId,title,updatedAt,active}]`); `showChatLoading` (`sessionId`,`title`,`mode:'load'` — pending load, cleared by `showChat`/`showEmpty`); `showChat` (`sessionId`,`messages`,`plan` — also used to render an optimistic empty chat for a pending `new` session); `showEmpty`; `showSessionPicker`; `showConfigRequired`; `showWorkspaceModeRequired` (blocking onboarding screen); `updateTokenUsage` (`usage`,`tokenLimit?`); `updateAgentRunning` (`running`); `updateMergeState` (`canMerge`); `searchFilesResult`; `streamChunk` (`sessionId`,`index`,`blocks`); `updateAutoAllowPermissions` (`value`); `restoreDraft` (`text`,`attachedFiles`); `updateAgentInfo` (`agentInfo`); `updatePromptCapabilities` (`{ image }`); `updateColorTheme` (`{ name }`); `resolveFileLinksResult` (`requestId`,`resolved`); `addDroppedFilesResult` (`files`,`rejected`).

## 6. Development and Operations

- **Build commands** (no generic `build` script):
    - `npm run compile` — one-shot esbuild of extension (`out/extension.js`, CJS) + webview (`out/webview.js`/`out/webview.css`, ESM).
    - `npm run watch` — esbuild watch mode.
    - `npm run lint` — ESLint over `src/` only (webview not linted). Config is warning-heavy (`curly`, `eqeqeq`); new code should avoid triggering.
    - `npm run install-local` — builds production, packages `.vsix`, installs into VS Code (no version bump).
    - `npm run release -- [patch|minor|major]` — bumps version (default `patch`), builds production, packages `.vsix`, commits `release: vX.Y.Z`, tags `vX.Y.Z`, pushes commit+tag to `origin` and `github` remotes, creates GitHub Release with auto-generated notes and attached artifact (requires `gh` CLI authenticated). Artifact is `exo-<версия>.vsix`.
